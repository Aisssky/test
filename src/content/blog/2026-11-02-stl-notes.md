## STL\(Standard Template Library\)

### 1、标准库以头文件方式呈现

- C\+\+标准库的头文件，不带副档名（\.h）

- 新式C头文件不带\.h，但加 c 前缀；例如 \#include \<cstdio\>

- 旧式C头文件仍然可用，兼容用；例如\#include \<stdio\.h\>

### 2、新式头文件内的组件封装于namespace "std";

- using namespace std;

把标准命名空间 `std` 里的名字“引入”当前作用域，使可以省略 `std::` 前缀，编译器会把这些名字当作在 `std` 里查找，于是等价于：

- using std::cout;

只是名字查找的便利写法，不会加载任何库，也不会复制代码。它只是省略前缀的语法便利，不是必须的。实际工程中更推荐显式写 `std::`，或者在局部按需 `using std::vector;`，尤其不要在头文件里写 `using namespace std;`。

- 当然，在实际的工程中，业务代码几乎完全不会使用原生STL，比如UE就有自己的组件，例如TArray，FString，TMap等，与GC和反射系统深度集成的这样的一套新东西，我们之后再探讨[UE中对于容器的处理](https://devpress.csdn.net/awstech/6a91f06c3bda720d4b35c87a.html)。

### 复杂度

目前常见的 Big\-oh 有下列几种情形：

1. O\(1\)或O\(c\)：称为常数时间\(constant time\)

2. O\(n\)：称为线性时间\(linear time\)

3. O\(log₂n\)：称为次线性时间\(sub\-linear time\)

4. O\(n²\)：称为平方时间\(quadratic time\)

5. O\(n³\)：称为立方时间\(cubic time\)

6. O\(2ⁿ\)：称为指数时间\(exponential time\)

7. O\(nlog₂n\)：介于线性及二次方成长的中间之行为模式



### C\+\+11 新特性

- 自动类型推断（auto）：引入了auto关键字，可以根据变量初始化表达式的类型自动推断变量的类型，使得代码更具灵活性和可读性。

```C++
// C++98 写法
vector<int>::iterator it = v.begin();
// C++11 写法
auto it = v.begin();

for (auto x : v) { ... }        // 拷贝一份（修改不影响原容器）
for (auto& x : v) { x *= 2; }   // 引用（能改到原元素）
for (const auto& x : v) { ... } // 只读，且不拷贝（遍历大对象首选）
```

- 范围for循环：通过for\(element：container\)语法，允许直接遍历容器中的每个元素，简化了迭代操作，减少了代码量。

auto类型推导的原理是什么？

auto类型推导的原理：编译器根据初始值来推算变量的类型，要求用auto定义变量时必须有初始值。编译器推断出来的auto类型有时和初始值类型并不完全一样，编译器会适当改变结果类型使其更符合初始化规则。**auto 会剥掉引用和顶层 const，要保留就自己写 auto\& / const auto\&**。想知道“原样类型”，用 decltype。

###### 底层

###### 核心数据结构

```C++
template<class T, class Alloc = allocator<T>>
class vector {
    T* begin_;      // 指向第一个元素
    T* end_;        // 指向最后一个元素的下一个位置（size 的边界）
    T* cap_end_;    // 指向已分配内存的末尾（capacity 的边界）
};
```

```Plain Text
size()     = end_ - begin_;
capacity() = cap_end_ - begin_;
empty()    = begin_ == end_;
```

> **注意 end\(\) 的位置**：它指向**最后一个元素的下一个位置**，是“哨兵”，不能解引用（\*v\.end\(\) 是未定义行为）。所以区间永远是**左闭右开** \[begin, end\)——这也是 STL 所有算法统一约定的区间形式。
> 
> 

- `size` 以内是“已构造对象”；

- `size` 到 `capacity` 之间是“已分配但未构造的原始内存”；

- 分配器负责“分配原始内存”和“构造/析构对象”这两件事的分离。

###### 扩容机制

当 `size() == capacity()` 时，再插入元素就必须扩容。以 `push_back` 为例：

```JavaScript
void push_back(const T& x) {
    if (end_ != cap_end_) {
        // 还有空闲槽位，直接原地构造
        construct(end_, x);
        ++end_;
    } else {
        // 满了，扩容
        reallocate_and_push_back(x);
    }
}
```

1. 申请一块更大的新内存（new\_capacity）

2. 把旧元素“移动/拷贝”到新内存

3. 在新内存末尾构造新元素

4. 析构旧内存上的所有元素

5. 释放旧内存

6. 更新 begin\_ / end\_ / cap\_end\_

###### 迭代器失效规则

所以迭代器失效的本质就是是否扩容？并不是，更准确地说：

> 扩容是导致“全部迭代器失效”的强原因之一，但迭代器失效的本质不是“是否扩容”，而是“该迭代器所指向的元素地址是否改变 / 元素是否被销毁 / 底层存储结构是否被破坏”。
> 
> 

对 `vector` 来说，因为迭代器本质上就是（包装过的）指针，所以可以理解为：

> 迭代器失效的本质 = 这个迭代器指向的内存位置，在操作之后不再对应原来那个元素，或者不再合法。
> 
> 

扩容只是让“所有元素地址都变了”的一种情况。未扩容的 `insert`、`erase`、`resize` 缩小、`clear` 同样会导致失效。

### 注意

1. **不要使用泛型的 sort**，list 有排序成员函数 list\.sort\(\)

2. 某些 Linux 下的 GCC 版本，对 list\.size\(\) 调用有性能问题，如果可以尽量避免使用，遍历链表建议使用迭代器

> **补充 · 为什么 list 不能用 std::sort**：std::sort 要求**随机访问迭代器**（要能 it \+ n、能算距离做快排的三数取中），而 list 只提供**双向迭代器**（只能 \+\+/\-\-）。所以标准库给了成员版 list\.sort\(\)——归并排序实现，只依赖双向迭代器，稳定，O\(nlogn\)，不占额外数组。
> 
> 同理 forward\_list 有 sort\(\)，但不能用 reverse 之外需要双向移动的算法。
> 
> **底层**：每个元素一个独立节点，节点里存 prev/next 两个指针 \+ 数据。所以「任意位置插删 O\(1\)」的前提是**你已经拿到了那个位置的迭代器**；如果只知道下标，还得先 O\(n\) 走过去。代价是每存一个元素要多付两个指针，且内存不连续、缓存不友好——这也是实践中 vector 常常比 list 快的原因。

##### set

###### 注意

1. **set 不要使用泛型的 lower\_bound 和 upper\_bound**，时间复杂度有问题

2. set 的移动迭代器 \+\+ 和 \-\- 操作的时间复杂度为 O\(logn\)

3. 不要边插边删

> **补充 · 为什么泛型版本会慢**：std::lower\_bound 是「二分」，它靠 it \+ n 跳位置——但 set 的迭代器只能 \+\+/\-\-，泛型算法只能退化成**线性前移**，O\(n\) 而不是 O\(logn\)。成员版 s\.lower\_bound\(x\) 直接在红黑树上二分，才是真 O\(logn\)。**凡是有同名成员版的算法，优先用成员版**（set::find、map::find、list::sort、list::remove…）。
> 
> 红黑树是「近似平衡」的二叉搜索树，最坏树高仍是 O\(logn\)，所以增删查都稳定在 O\(logn\)。代价是每个节点额外存颜色和三个指针，内存开销明显大于 vector。

#### 容器适配器

|适配器|语义|默认底层容器|说明|
|---|---|---|---|
|stack|后进先出 LIFO|deque|只暴露 push/pop/top/empty/size|
|queue|先进先出 FIFO|deque|只暴露 push/pop/front/back/empty/size|

注意：

- **适配器不提供迭代器**，只暴露有限接口——所以不能对 stack 做 for 遍历，也不能传给 sort。

- 适配器可以换底层：stack\<int, vector\<int\>\>、queue\<int, list\<int\>\> 都合法（换的容器得支持所需操作）。

> **补充 · 三者的底层**：stack/queue 只是把底层容器的接口“掐头去尾”露出来；priority\_queue 靠 make\_heap / push\_heap / pop\_heap 这组堆算法维护 vector 里的完全二叉树结构，所以 top\(\) 是 O\(1\)、push/pop 是 O\(logn\)，而它的迭代器？没有——堆的内部数组顺序不是有序的，暴露迭代器会误导人。
